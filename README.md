# Introduction

This project is a proof of concept showing how an LLM firewall can inspect SQL
generated by a locally running Ollama model before that SQL reaches PostgreSQL.
It is intentionally simple and is not intended for production use.

# How to run the stack

Run all commands from the repository root.

## 1. Create the Python environment

This project requires Python 3.10 or newer.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirments.txt
```

If the virtual environment already exists, only activate it and install any
missing dependencies.

## 2. Configure and run PostgreSQL

Create the database environment file:

```bash
cp configurations/.env.example configurations/.env
```

Open `configurations/.env` and replace the example password with a local
password of your choice. This file is ignored by Git.

Start PostgreSQL in the background:

```bash
docker compose -f configurations/docker-compose.yml up -d
```

Check that the database is healthy:

```bash
docker compose -f configurations/docker-compose.yml ps
```

The first startup creates the `customers` table and inserts fictional sample
data from `configurations/postgres/init/`.

To inspect the data directly:

```bash
docker compose -f configurations/docker-compose.yml exec database \
  psql -U firewall_user -d firewall_bank
```

Then run:

```sql
SELECT * FROM customers;
```

Type `\q` to leave the PostgreSQL shell.

## 3. Run Ollama

Make sure Ollama is installed, then download the default tool-capable model:

```bash
ollama pull qwen3.6
```

If Ollama is not already running as a background service, start it in a separate
terminal:

```bash
ollama serve
```

The application expects the Ollama API at
`http://localhost:11434/api/chat`.

## 4. Run the protected demonstration

The firewall is enabled by default:

```bash
python main.py
```

You can select another locally installed, tool-capable model:

```bash
python main.py --model qwen3
```

In protected mode, SQL such as `SELECT` is allowed while modifying statements
such as `INSERT`, `UPDATE`, `DELETE`, and `DROP` are blocked.

## 5. Run the unprotected demonstration

To demonstrate the risk of executing model-generated SQL directly:

```bash
python main.py --disable-firewall
```

This mode deliberately allows model-generated SQL to modify the demonstration
database. Use it only with the local fictional data included in this project.

Type `exit` or `quit` in either mode to end the conversation.

## 6. Stop the database

```bash
docker compose -f configurations/docker-compose.yml down
```

PostgreSQL data is stored in a Docker volume, so this command stops the
container without deleting the data. The initialization SQL files run only when
the database volume is created for the first time.

# How the code works

- `main.py` reads the command-line options and starts an interactive chat.
- `llm_integrations/ollama_based_integration.py` sends the conversation and
  database tool definition to Ollama through `POST /api/chat`.
- When Ollama requests `execute_database_query`, the integration passes its SQL
  to `llm_integrations/database_layer.py`.
- With the firewall enabled, the database layer sends the SQL through
  `firewall/firewall_class.py` before execution.
- With the firewall disabled, the same SQL is sent directly to PostgreSQL.
- The database result or firewall error is returned to Ollama as a tool message.
  Ollama can then produce its final answer for the user.

The application, rather than the model, controls whether the firewall is
enabled. This prevents the model from selecting the unprotected execution path
through a tool argument.
